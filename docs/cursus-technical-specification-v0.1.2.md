One operator, one orchestrator process, one runner host, one database. M5 and a second runner are outside this implementation. Use existing browsers on MyPC and Chromebook. Agent and verifier commands are scoped to approved trusted repositories and authorized task types.

## 3. Dependencies

**[PROPOSED DESIGN DECISION]** Target CPython 3.12+ and PostgreSQL 16+ on the VPS Linux installations. Direct application dependencies are FastAPI, uvicorn, Jinja2 and asyncpg. Use the Python standard library for runner TLS HTTP, TOML, subprocess supervision, JSON, hashing, and testing. Serve a pinned htmx distribution locally. The package build may run on CI or an admin workstation. Git, Tailscale Serve, systemd, PostgreSQL client tools, Hermes scheduling and the four agent CLIs are host tools. No SDK wraps the CLIs or OpenCode Go. Python does not call model APIs directly.

Before selecting exact versions, inspect direct and transitive license evidence, exclude incompatible licenses, and lock artifacts and hashes for reproducible installs. Vendor only htmx and its license. Record binary versions, measured wire formats and credential renewal in the M0/M1 evidence. A new CLI version requires requalification of its affected capability profile before use.

## 4. Configuration

**[PROPOSED DESIGN DECISION]** Read each process's TOML and secret files only at startup. Config validation is strict. Unsupported keys, unknown IDs, prohibited providers, contradictory tool rights, a dirty role/prompt release, or an invalid capability digest fail startup for the affected process. Reconfigure by deploying committed files and restarting at an appropriate time. Jobs already queued use their immutable invocation inputs, not the currently loaded registry.

| Configuration group | Required values and validation |
| --- | --- |
| VPS-B service | Loopback bind, Unix socket, external HTTPS origin, exact operator Tailscale login, local DSN path, artifact root, runner ID and bearer digest, per-repo enrollment, backup paths |
| Repository enrollment | Operator-approved GitHub owner/repo, allowed target refs, named verification commands with literal argv, allowed relative cwd, timeout, and phase check IDs. Code checks require at least one enrolled phase command. Commands cannot interpolate agent content or invoke an implicit shell. |
| VPS-A service | Tailnet HTTPS origin, runner ID, bearer secret file, persistent state root, per-CLI absolute binary/user/home, production slot users, separate read-only reviewer/verification execution identities, Git and GitHub credential paths, measured capability profile |
| Role release | `schema_version=1`; role ID, tier, CLI, prompt path, tool allowlist, timeout, model and reasoning settings where supported, and pi provider where applicable. Reject wildcard tool authority. Record commit, profile digest and exact prompt content in jobs. |
| Defaults | **[PROPOSED DESIGN DECISION]** Two pi execution slots, one verifier slot, one frontier slot, one repository slot, 30s long poll, 10s heartbeat, unreachable indicator after three missed heartbeats, 2 repair retries after initial candidate, 2 interrupted retries per logical step, 3 debate rounds, 10 debug turns, 20 interview rounds. Configurable positive limits except the three-round maximum. Bounds are adjustable after VPS load tests. |

Preserve space for terminal records and control events. Refuse admission on insufficient reserve. |

Disable any workflow or automation that would merge or push to the target as a side effect of Cursus publication. CLIs have native credentials scoped to their own users. The pi provider default is OpenCode Go, model `deepseek-v4.1-flash`. Provider, model and reasoning settings are selected by the operator in the registry and verified together as a supported tuple. This is static configuration, never scheduling policy.

### 4.1 Capability qualification

The measured profile records binary digest and version, privilege identity, fixed argv tokens and prompt transport, supported roles/models/tool mappings, structured success/failure signatures, and successful probe evidence. A profile contains concrete qualified values, never guessed switches. Input text is data passed via the documented stdin or argument path, never a shell command. M1 gates activation of a role until its measured literal fixtures demonstrate that the required behavior works on VPS-A. M3 browser functionality depends on the M1 Serve identity probe. Missing mandatory capability blocks milestone acceptance and causes a supported configuration fix or a specification revision.

| CLI | Invocation contract to qualify |
| --- | --- |
| pi | Direct `pi --mode rpc` for long turns and `pi --mode json` for one-shot roles. Qualified flags select provider/model/reasoning, allowed tools and clean configuration. Test real Go tool calls and return parsing. RPC lines correlate prompt, steer and abort responses by ID. Idle steering uses a new prompt under the same session, active steering uses the measured steer operation. A steer response establishes acceptance, not model consumption. Identify assistant final message and turn terminal events from the installed version. [pi RPC reference](https://upd.dev/badlogic/pi-mono/src/branch/argument-finalization/packages/coding-agent/docs/rpc.md) · [OpenCode Go endpoints](https://opencode.ai/docs/console/go#endpoints) |
| Claude | Direct `claude -p --output-format stream-json`, with installed-version options needed for headless streaming and read-only operation. Verify the final result, rejection/auth behavior, and disabled shell/write/MCP capabilities. |
| Codex | Direct `codex exec --json` in read-only mode with qualified approval and config isolation. Parse terminal turn and assistant result from JSONL. Prevent project MCP and tool config from reintroducing write authority. [Codex non-interactive reference](https://learn.chatgpt.com/docs/non-interactive-mode) |
| Antigravity | Direct `agy -p --output-format stream-json`, with native cached authentication and verified read-only execution. Consume incremental events and terminal result. **[CONFLICT]** The brief's `json` form emits a single final object. Use the D1 §11 stream choice to meet live events. [Antigravity headless reference](https://antigravity.google/docs/cli/headless/) |

## 5. Data Layer

### 5.1 Closed contract vocabulary

Names in backticks in the contract sections denote shared types unless they are a literal, path, module or member. Scalar rules apply at all entry points.

| Type | Definition and consumer |
| --- | --- |
| `Id`, `Time`, `Seq`, `Digest`, `Sha`, `Ref` | UUID, UTC RFC3339, positive bounded int64, lowercase SHA-256 hex, lowercase full Git object SHA under the enrollment's object format, fully qualified Git branch ref validated by Git. At-rest timestamps use timestamptz; hashes and refs are strings. API contracts consume these. |
| `Repo`, `FileRef`, `Candidate`, `PullRequest` | Repo = enrolled owner/name + target Ref. FileRef = id, digest, length, safe display name and media type. Candidate is code (Repo, pinned base Sha, attempt Ref, head Sha) or files (nonempty ordered FileRef list). PullRequest = Repo, head Ref, validated head Sha, number and GitHub URL. Consumed by Job and verifier/reviewer/publication. |
| `Role`, `Invocation` | Role = name, tier, CLI, model/provider/reasoning where supported, allowlist, prompt path and limits (§4). Invocation = Role snapshot, registry commit, profile digest, rendered prompt text. Consumed by Job and execution. |
| `Criterion`, `Evidence`, `Plan` | Criterion = id, requirement text and one check from §8.3. Evidence = criterion id, candidate identity or staged tree Sha, applicable observed values, pass/fail, verifier attempt id, optional FileRef log. Plan = ordered packages (stable ID, dependencies, objective, inputs, criteria), phase check IDs and optional ordered delivery groups (group ID and member package IDs). Consumed by workflow decisions. |
| `Input`, `Action` | Input = workflow (code, debug, marketing, grant, business), form (one-shot, ticket, phase for code), source (inline text, repo/commit/path, or interview), optional Repo required for code/debug, plan debate and spec debate booleans. Action union = submit(Input), answer(phase id, question id, text), steer(attempt id, text), cancel(phase id), declare_unrecoverable(attempt id, reason), abandon(attempt id, reason). Consumed by control and UI. |
| `Job` | ID, phase ID, optional package ID, logical step, immutable input data, required slot, optional Invocation and optional publication intent ID. Logical steps and their input/result pairs are listed in §8.2. Consumed by runner dispatcher. |
| `Claim`, `Observation`, `Poll` | Claim = Job, attempt id, assigned runner ID and claim request UUID. Observation = attempt id + one of never_started, live, terminal_pending, stopped, unknown, with reason and optional terminal sequence. Poll = current runner ID and optional Claim. Consumed by runner and control. |
| `Command`, `CommandResult` | Command = ID, attempt ID, action (steer, stop, continue_debug, finish_debug), optional text or checkpoint and verification payload according to §8.4, issuance event Seq. CommandResult = command ID, disposition (accepted, rejected, target_finished, uncertain, stopped), optional reason. Consumed by runner journal and control. |
| `Event`, `Final`, `Ack` | Event = attempt id, Seq, kind and payload. Kinds and payloads are started (service activation and start time), log (stream class and sanitized text), usage (available nonnegative input/output tokens and optional currency and decimal cost), command_result (CommandResult), debug_checkpoint (code Candidate, turn number and completion report) and final (Final). Final = completed (step-specific value), failed (classification/diagnostic), interrupted, canceled, or unknown, plus reason when applicable and stopped-execution evidence when claimed. Ack = highest committed contiguous Seq (0 if none), permitted disposition active/terminal/stale and next expected Seq. Consumed by replay and workflow progression. |
| `Heartbeat`, `Recovery`, `Directive` | Heartbeat = running/allocated slot counts, spool bytes, runner boot identity and latest local health. Recovery = persistent runner generation, observations, locally outstanding claim request IDs and, during restore, the locally retained publication intent descriptors. Each descriptor contains intent ID, phase ID, repo, refs, expected/desired Sha where applicable and job step. A descriptor reports evidence and grants no authority. Directive = held claims, queued commands, ack per reported attempt, reconciliation complete flag and apply dispositions (resume, replay, ignore-stale, stop-stale, await-reconciliation). Consumed by control and runner. |
| `View`, `EventPage`, `Reply`, `Problem` | View = authorized phase/attempt/operator snapshot, with choices, summaries and cursor. EventPage = ordered committed audience events, cursor and reset flag. Reply = resulting entity ID, state, revision and last committed cursor. Problem = stable error code, safe message and optional entity ID. Consumed by HTTP and operator CLI. |
| `Decision`, `Snapshot`, `Change` | Snapshot = authoritative state rows and pinned inputs for one transition. Change = new operator action, accepted Final, debug checkpoint, or confirmed observation. Decision = row mutations, new jobs/commands and domain events. Consumed by control and store. |

For logical signatures, a path is an absolute local string or an explicitly marked repo-relative POSIX string. A stream is ordered bytes or its declared frame type. Process kind is control/runner/operator_cli. A principal is operator login, local operator group identity or enrolled runner ID as determined by ingress. Maintenance disposition is defined in §15.3. View carries entity ID, workflow/status, package and attempt states/reasons, runner and usage projection, authorized pending actions, reference list and cursor. EventPage items contain cursor, time, phase/optional attempt ID, kind and sanitized payload. UUID-bearing forms and JSON share field names. Optional inputs are omitted rather than silently defaulting to another union variant.

The step-specific values embedded in Final and Job are closed by §8.2. Union discriminators are required. Wrong variant, foreign entity ID, unknown field and invalid enum are validation failures. Server-created timestamps are authoritative for cursor-independent chronology. Only execution-result timestamps carry runner clock as informational data.

Identifiers on JSON objects use snake_case. Every mutation includes a UUID (header Idempotency-Key where used by §6, hidden request_id for browser forms). Required protocol fields use the exact names listed here. Time values are UTC.

| Message | Field keys and edge rules |
| --- | --- |
| Input | workflow, form, source, repo, plan_debate, spec_debate. Inline source carries kind and text. Repo source carries kind, enrolled owner/name, commit and path. Interview source carries kind only. Repo carries owner, name, target_ref. Code/debug require repo. Form applies only to code and defaults to phase. |
| Action | kind plus input for submit, phase_id/question_id/text for answer, attempt_id/text for steer, phase_id for cancel, or attempt_id/reason for the two exceptional recovery actions. |
| Job and Claim | Job fields id, phase_id, optional package_id and group_id, step, input, slot, optional invocation and publication_id. Claim fields job, attempt_id, runner_id and request_id. Slot values worker, verifier, frontier and repository. The repository slot is a single separate lane on VPS-A. |
| Heartbeat and Recovery | Heartbeat fields slots, spool_bytes, boot_id and health. Slots are counts by slot kind. Recovery fields generation, observations, pending_request_ids and optional publication_descriptors during restore. Each Observation has attempt_id, kind, reason and terminal_seq where applicable. |
| Directive | held_claims, commands, ack_by_attempt, reconciled and dispositions by attempt ID. Commands carry id, attempt_id, action, issued_seq and only applicable text, checkpoint or evidence fields. |
| Event & Ack | attempt_id, seq, kind, payload. Ack fields committed_through, disposition and next_expected. Event payloads use the named scalar or structured members in the event contract. Store a digest of canonical validated JSON for each accepted attempt sequence. |
| Operator query/result | Return cursor with each View/Reply. Reply fields entity_id, state, revision and cursor. Problem fields code, message and entity_id when safe. |
| Artifact | Headers Content-Length, Content-Type, X-Cursus-Sha256 and X-Cursus-File-Name on upload. Return id, digest, length, name and media_type. File-name value is percent-encoded UTF-8; reject control characters, slash, backslash and dot traversal after decoding. |

Use integers for ordinal, count, byte length and limits. Optional union data must match the discriminator. JSON digest canonicalization is compact UTF-8 with sorted object keys, preserved array order, no non-finite numbers, and no duplicate keys. Validate type before calculating request identity. No floating-point value is required by workflow decisions. Cost, where present, is a decimal string with currency.

### 5.2 PostgreSQL relations

All IDs are primary UUIDs unless stated. Each FK refers to the corresponding table ID. FK integrity and uniqueness are database invariants, with semantic transition guards rechecked inside transactions.

| Relation | Required columns and constraints |
| --- | --- |
| coordination | Singleton row, next operator-visible event cursor, restore/drain state. Lock first for mutations in v1. |
| request_keys | Principal, route, request UUID composite key, request digest, response status/body. Record in the operation transaction. |
| phases, specs, plans | Phase ID, workflow/repo/target, phase state, spec and plan revision pointers, registry snapshot, integration lane IDs, delivery/failure reason. Specs and plans keyed by phase and positive revision with immutable payload. |
| integration_lanes | Unique phase/group, pinned target Sha, current integrated Sha, last confirmed remote integration Sha (nullable before first push), state and optional PullRequest. |
| packages | Phase FK, plan revision, package ID, state, dependencies, criteria, accepted result identity, active owner attempt FK, repair and interruption counters. Unique phase/plan/package. At most one ownership slot per row. |
| jobs | Phase/package/lane linkage as applicable, step, immutable Job payload, step ordinal, queued/claimed/done state, assigned attempt, scheduling key, creation cursor. Unique phase/step/scope/ordinal prevents duplicate enqueue. Index queue state, slot, order. |
| runners, attempts | Runner ID, enrolled generation, last contact/health. Attempt FK to Job, runner, claim request, phase/package, status, checkpoint, ack Seq, ownership/terminal disposition and evidence. Unique runner/claim request and one attempt per issued job row. Retry inserts a new job and attempt. |
| commands | Attempt FK, sequence, action, text, state, result. Unique command ID. No command transfer between attempts. |
| events | Committed cursor primary key, phase/attempt, source Seq where applicable, event class, timestamp and validated payload. Unique attempt/source Seq. Append-only during retention. |
| artifacts | Artifact ID, source attempt, digest, length, media/name, relative storage location, staged/ready lifecycle. Unique attempt and caller-generated file ID. |
| publications | Intent ID, phase FK, kind, repo, designated head/base refs, expected old integration Sha, verified new Sha, state, PR identity and exact returned result. One unresolved mutation intent per phase integration lane. |
| migration_history | SQL version and applied digest. One migration lock. |

**[PROPOSED DESIGN DECISION]** Serialize v1 control mutations through the singleton row. This ensures a cursor issued in a later transaction cannot become visible before an earlier cursor, and keeps the atomic transition protocol simple. Claims also select an eligible queued job `FOR UPDATE SKIP LOCKED` and insert one attempt. Commit state, queued work, events, and idempotency record together. Send PostgreSQL notifications on commit; a periodic scan covers missed notifications. Do not hold this lock while calling network, CLI or artifact filesystem writes. Downloads hold an open file handle so cleanup cannot interrupt an active read.

## 6. API Specification

### 6.1 Common rules

JSON for runner exchanges and the operator CLI; server-rendered HTML/form representation and SSE for browser routes. Operator CLI uses the local Unix socket and the same action/query contracts as the browser. Every state mutation uses a caller-generated request UUID or an already-defined attempt sequence/command ID. Reusing a request key with different input returns 409. Every runner exchange carries the enrolled generation in a dedicated header alongside its bearer. The control process starts with runner admission closed until authenticated reconciliation has completed. Link failures cause the runner to reconcile before attempting a new claim. Endpoint authentication precedes parsing beyond the configured body limit. Return Problem on error (§11). Serve only the configured origin, with per-route limits.

### 6.2 Operator endpoints

| Method and path | Input → output | Behavior |
| --- | --- | --- |
| GET `/`, `/phases/{id}`, `/attempts/{id}` | Optional pagination cursor → View | Project committed phase/attempt states, controls, provider usage, questions, parked reasons and delivery links. |
| POST `/operator/actions` | Action + request UUID + browser CSRF field → Reply | Submit or answer; steer eligible current pi attempt; cancel phase; explicitly declare an unrecoverable attempt or abandon an existing unresolved parked attempt. State/permission preconditions in §8. |
| GET `/phases/{id}/events` | Last-Event-ID or cursor → EventPage streamed as SSE | First query committed events after cursor. Send cursor as SSE id. Wait for notification or 5s poll, then query again. On retention/reset emit reset and close. Send comments for keepalive. |
| GET `/artifacts/{id}` | ID → validated bytes | Operator-only download for ready artifacts authorized by their phase. Escape filename; download as attachment, never active inline HTML. |

Browser behavior includes reading committed history, reconnecting SSE without duplicate application, submitting an interview reply, viewing pending versus confirmed cancellation and steering, recording recovery reasons and accessing exact PR or file results. Use htmx and minimal same-origin browser code where required to open SSE and resync. The operator-approved design handoff defines UI visuals. Use it to implement server-rendered templates and local assets within the contracts in this section. Browser actions have no arbitrary shell, credential admin or target merge controls.

### 6.3 Runner endpoints

| Method and path | Input → output | Behavior |
| --- | --- | --- |
| GET `/jobs/next` | Request UUID, available slot kind → Poll or 204 | Side-effecting long-poll retained from D1 §6. Require bearer and no-store. Remember a granted claim under its request UUID. During restore drain, allow only an authorized read-only reconcile_publication claim, after runner identity and observations have been reconciled. Normal claims require completed recovery and reopened intake. |
| POST `/runners/{id}/heartbeat` | Heartbeat → Directive | Update liveness and return unresolved commands addressed to held attempts. |
| POST `/runners/{id}/reconcile` | Recovery → Directive | Gate new claims until locally known and server-held attempts are reconciled. Reissue ambiguous grants, report stale IDs and provide committed event positions. |
| POST `/attempts/{id}/events` | Ordered Event array → Ack | Accept new contiguous sequences, discard digest-equal repeats, reject gaps/content mismatch and bind events to runner and attempt. Stale attempts cannot progress the phase. |
| PUT `/attempts/{id}/artifacts/{file_id}` | Raw bytes + digest, length, media and name → FileRef | Stage, hash, atomically publish bytes and insert metadata. Deduplicate identical retries; digest or metadata mismatch is 409. |
| GET `/runner/artifacts/{id}` | ID + current claim ID → FileRef metadata and bytes | Read only new-job inputs explicitly listed in the claim and previously committed ready. Validate digest locally before use. |

A runner starts every request for new work with a locally recorded request UUID. When no work is granted it may retire the UUID after observed 204. An unobserved 204 has no durable side effect. On recovery, if a previously requested UUID has a claim and the complete local journal proves no launch intent ever existed, return the existing claim for first launch. If journal integrity or scope is uncertain, recovery cannot infer never_started from absence. Authenticated requests remain scoped to the assigned runner ID even if another tailnet node can reach Serve.

## 7. AuthN/AuthZ

**Browser.** Tailnet Serve HTTPS → loopback FastAPI. Read the canonical `Tailscale-User-Login` header only on the Serve-facing listener. Require exact operator match, reject missing/duplicate identity, test injected headers, and disallow other local app identities reaching the loopback trust boundary through host isolation. VPS-B is dedicated to trusted services. Use a host-only, Secure, HttpOnly, SameSite session cookie with signed server-issued CSRF token and exact Origin validation for browser writes. Operator authorization never comes from a bearer token. [Tailscale Serve identity](https://tailscale.com/docs/features/tailscale-serve#identity-headers)

**Local CLI.** Unix socket with filesystem permission for configured local operator group, separate from the Serve ingress. No listener accessible to trusted-repo subprocesses. Socket-side operator requests bypass Serve identity only at that protected ingress. State mutations have the same eligibility rules as browser actions.

**Runner.** Authenticated by bearer secret and allowed tailnet node. Verify token digest in constant time and scope runner resources. Stop work intake when token invalid; already-running local work can finish and spool. Only the control service uses DB credentials. Secrets never enter command/model prompts, repo trees or response bodies.

**VPS-A privilege boundary [PROPOSED DESIGN DECISION].** Runner service starts trusted Python under a privileged service identity so it can switch subprocess UID/GID before exec. Give the parent a narrow startup configuration and a runner-owned, inaccessible state/credential root. Distinct unprivileged users handle pi slots, verification and the three frontier CLIs. Drop elevated credentials and supplementary groups before exec. Agent/verifier processes lack the runner and GitHub credentials and cannot write each other's workspaces. Frontier tools see a runner-owned read-only snapshot and a private home; disable shell, write/network tools and project-discovered configuration that can register tools. Native provider egress remains available to each approved CLI. No alternate launcher bypasses direct CLI invocation. Disable repo-local hooks and external diff/filters for runner-owned Git operations. Never invoke repository code with runner credentials. Verify socket, process, credentials and filesystem boundaries in §12.

**GitHub.** Runner-owned publisher has repository-restricted write credentials furnished at deployment, validated for each enrolled repo, and only invokes approved Git/PR operations. Branch prefix and repo/head/base are computed from persisted identities, never accepted from CLI output as authority. Deny arbitrary mutations and every target-ref push or merge. Where available, enable GitHub-side protection as defense in depth. GitHub auth and branch controls are measured with the actual enrolled repository settings.

## 8. Module Specifications

### 8.1 Composition and named entry contracts

These are logical signatures, not source code. A module name before a method identifies the owning component instance. Loaded settings, database pool, HTTP transport/client, template environment and execution dependencies enter through bootstrap. Constructor inputs are the concrete services listed here. No other module instantiates infrastructure.

| `http.serve` | Bind settings, Control, template/static access → service lifetime | Bind loopback and operator-only local socket, enforce §7, route §6. |

| `control.action` | Authorized operator identity, request UUID, Action → Reply | Idempotent operator transitions. |

| `control.query` | Authorized principal (operator or runner), entity route/ID, cursor, and current Claim for runner artifact reads → View/EventPage or FileRef | Read authorized committed state and download metadata. |
| `control.maintain` | Trigger (boot, timer, notification or backup request) → committed transitions or maintenance disposition | Drive periodic checks and restore/drain operation. |
| `workflows.decide` | Snapshot, Change → Decision or Problem | Pure deterministic transition rules, including job/result compatibility checks; no external I/O. Control invokes within a transaction. |
| `store.transact` | Typed Action, runner request or maintenance operation, and Control's transition callback where applicable → committed Reply/Directive/Ack/Poll/maintenance disposition or Problem | Own transaction boundaries, lock ordering, snapshots, mutation/notification, audit, and idempotency. |
| `store.migrate` | Ordered packaged SQL bytes and lock → applied revision or startup failure | Bootstrap runs migrations before listening. |
| `store.read`, `store.wait` | Authorized query key and cursor → View/EventPage/FileRef; deadline or notification → wake/timeout | Control reads, and HTTP SSE/claim waits outside transactions. |
| `artifacts.stage`, `artifacts.open` | Claim, metadata and stream → FileRef plus private staged path result; FileRef → verified byte stream | Control on upload and HTTP on authorized download. Stage fsyncs and publishes at the immutable path before metadata commit. |
| `runner.serve`, `runner.exchange` | Validated settings and process-injected resources → service lifetime; runner route and request from §6.3 → typed response or classified transport failure | Bootstrap starts service. Runner service drives HTTPS with bounded waits and backoff; only this loop initiates exchanges. |
| `runner.record` | Local record update (claim, launch intent, started, output/checkpoint, command attempt/result, final, or ack) → durable sequence or local write failure | Append and sync local journal before effects or acknowledgments as specified in §§8.4–8.5. |
| `execution.run` | Job and path to isolated workspace, authorized UID/GID, event sink, and for RPC an in-flight Command stream → Final or debug checkpoint stream and Final | Direct agent/verifier launch, framing and normalized execution result. Runner supplies and drains sinks. |
| `repository.perform` | Job or runner execution setup/result, recorded GitHub intent when applicable, and workspace root → prepared snapshot/path, Candidate, or step-specific Final/Problem | Runner prepares worktrees, stages output, performs privileged publishing, and reads immutable repo inputs. |

Constructor responsibility is explicit. `bootstrap.py` creates one config per mode. For control it creates asyncpg pool, Store, Artifacts, Control (with Workflows' decision function), template environment and HTTP service. Runner mode creates the HTTPS client, Repository (with the trusted Git/GitHub transport), Execution, and Runner with the journal root. Local CLI mode constructs the socket transport and calls `http.request_local`. Each entry-point lifetime starts and closes only its own resources. The runner and control are separate processes even though they share the composition module.

### 8.2 Work item and result contracts

A Job has precisely one of the following steps. Input and result columns specify the concrete payload variations consumed by `runner.serve` and `workflows.decide`. Unless a result explicitly uses an existing candidate, it carries the job's phase/job identity by its attempt envelope. For an orchestration response, parse one strict JSON object from the final assistant response. Free-form reasoning or log text never changes state.

| Step | Job input | Completed value and origin |
| --- | --- | --- |
| `resolve_input` | Enrolled Repo + exact source commit/path or selected target Ref, with optional inline spec | Exact UTF-8 bytes and source commit when applicable, plus target base Sha for code/debug. Repository fetches from GitHub and reads the blob without executing it. |
| `interview` | Transcript, current spec revision if any, missing questions from prior judge if any, and interviewer Invocation | Either numbered questions (stable IDs assigned by control, text, required flag) or a complete proposed text spec. No partial guessed spec is marked complete. |
| `plan` | Workflow, accepted spec, pinned Repo/base where applicable, enrolled check catalog, planner Invocation | Plan or an initial ScoutRequest (one question and declared prepared input references). Code one-shot and ticket each require exactly one package. Debug requires one package with enrolled reproduction/regression criteria. Non-code specifies artifact obligations. |
| `debate` | Mode, round, seat (rationale/critic/advocate reply/judge/author revision), eligible transcript projection and Invocation | Author rationale text for the rationale seat; critic list of objection IDs/severity/evidence/fix; advocate decisions by ID (concede/rebut/amend); judge rulings by ID, required amendments, spec questions and accept/continue; or revised Plan/spec. Each seat returns only its matching shape. Author rationale is captured with the initial plan/spec or elicited by a fresh rationale invocation before the first critic step. |
| `scout` | Planner-requested bounded read-only question and repo snapshot or files, pi Invocation | Structured findings and source references. The planner may request one validated scout in its initial result and then receives the findings on one re-invocation. A further scout request fails the plan. |
| `produce` | Package objective/criteria and prior findings, pinned phase head or input files, worker Invocation | Structured completion report (summary, suggested files from output directory) plus Candidate captured by runner. Git candidates have runner-generated immutable attempt or checkpoint refs and verified SHA. For files, only successfully ingested FileRefs are returned. |
| `debug` | Repo/base, reproduction and fix criteria, debug Invocation, turn budget | Checkpoint event holds a candidate SHA, turn ordinal and report. Final completed value points to the exact approved checkpoint and original report. Runner maintains a single pi RPC session until finish, stop or budget failure. |
| `verify` | Candidate or integration candidate, required criteria with expected inputs, enrolled commands | Complete ordered Evidence list, empty only where the workflow requires no verifier checks. Runner records actual command/artifact results. Exact reviewed identity is carried on every item. |
| `review` | Candidate, verification evidence, criteria, expected package/scope, immutable inspection inputs and independent reviewer Invocation | Verdict (accept, repair, or reject), per-criterion result, findings and required repairs. Accept requires all criteria resolved. |
| `stage_integration` | Repo, expected integrated phase head, package Candidate, expected patch identity or final target drift request | Candidate with exact integration Sha, prepared in a separate worktree and carried in a temporary non-target ref; patch identity; conflict classification or success. |
| `advance_integration` | Repo, recorded expected old head, verified staged head, authorized publication intent | Remote ref and Sha read back from GitHub, or typed ambiguous/mismatch failure. |
| `inspect_target` | Enrolled Repo and target Ref | Exact current target Sha fetched by repository. |
| `reconcile_publication` | Immutable publication intent, expected remote inputs | Confirmed prior result, proven no effect with safe retry, or unresolved/mismatch. Never writes remote refs or PRs. |

All build, integration and PR results come from runner-controlled operations. Use the minimum direct CLI event fields required for rendering change/log/usage, terminal result and control correlation. Record sanitized prompts before dispatch and normalized answers after ingestion. The validated pinned invocation profile owns vendor-specific raw event field mappings. Do not turn vendor format variations into a model routing abstraction.

**Roles.** Required roles are interviewer, planner/decomposer, worker, debug worker, scout, reviewer, three debate seats and verifier. Default interviewer and planner are Claude. Default reviewer is Codex, with a distinct pi role configurable. Testing uses deterministic runner commands, while any planned test creation uses pi. For debates bind one role per eligible frontier CLI, including Antigravity. Use the originating author CLI for advocate; for operator-authored raw specs, use the configured frontier spec author to formulate the first rationale. Judge and critic must be the other two. Reject invalid assignments at admission. Freeze the assignment for the entire debate. The same reviewer attempt cannot also own the candidate it reviews.

### 8.3 Workflow and evidence transitions

1. **Intake.** `submit` validates enrollment and milestone availability, pins roles and records inputs/revision 1. Repo-file intake first queues resolve_input. Code/debug pins the target Sha before execution even for inline specs. Guided intake starts interview. Ask the operator only while awaiting a required input. `answer` is legal for an open question on the current phase and accepted once. When all required questions are answered, queue a new interview with the transcript. A complete spec advances to optional spec debate or planning. At the configured round cap park with the unresolved information. Direct specs begin the same planning path. If spec debate asks questions, run interview against those question IDs and resume the next debate round with the new revision.
2. **Planning and debate.** Graph validation requires unique package IDs, known and acyclic dependencies and typed executable criteria. Review uses the exact revision. Optional structured debate processes author rationale → independent critic → advocate replies → judge → author update where required. A critic receives the plan/rationale and prior upheld findings, without the current replies. Later rounds focus on upheld items and amendment regressions. A judge accept or absence of upheld blockers closes after required amendments are validated. Three rounds with unresolved blockers park. An invalid output is classified and may consume an interrupted-step retry only if a transient cause is proven. Unresolved structural defects park.
3. **Readiness.** Sort ready packages by explicit plan order among eligible jobs. A package is ready once dependencies are integrated or accepted for files. Pin the current integrated head on admission of each coding production job. Dependent jobs retain explicit accepted artifact references. The controller reserves the package owner on first production/debug claim and keeps it until the attempt's completion, proven interruption/cancellation or abandonment. Auxiliary verification/review jobs carry their own attempts with at most one in-flight attempt per job and do not replace the production owner. Later progression refers to the accepted candidate ID.
4. **Verification.** Allowed criterion variants are `command` (enrolled command ID, expected exit status, optional required literal in bounded output), `file` (safe relative filename, expected media, length bounds and optional required literal in UTF-8 content) and `review` (explicit observable pass rule and required evidence references). Commands run at the pinned candidate SHA. For files, match uploaded bytes and recorded digest. For review criteria, the reviewer must record a pass/fail with criterion-linked evidence. Coding and debug handoff require enrolled phase checks, and debug requires reproducible evidence of fix or an explicitly defined regression check. Reviewer accepts only the candidate actually verified. Missing report, missing evidence, incomplete checks, or inconsistent identity cannot pass. A negative verdict consumes one bounded repair, supplies findings and prior candidate as inputs to a fresh pi attempt, or parks. Integration overlap uses the same repair budget. Operator cancellation suppresses retries.
5. **Debug loop [PROPOSED DESIGN DECISION].** After a pi turn yields a candidate report, the runner snapshots it and sends debug_checkpoint while retaining the running process and claim. VPS-B queues verification on that exact candidate using the separate verifier slot. Failed verification below the debug-turn limit sends an internal `continue_debug` command with bounded evidence and starts a new prompt in the same idle RPC process. Passing verification sends `finish_debug` for that checkpoint; the runner records successful terminal completion only after closing the process and checking that the selected snapshot is unchanged. The controller uses the committed checkpoint evidence to queue independent review. Review failure may start a new debug attempt within the repair budget. At the turn cap or absent reproducible evidence, park. No successful exit remains open for optional extra work.
6. **Integration.** Serialize one integration job chain per phase, from the planned ordering of accepted packages currently eligible for integration. Build the candidate in a separate worktree by applying only the accepted package delta to the current phase integration head. Store canonical delta identity over path/mode/content changes relative to the package base. Tests verify the combined commit. If applying the patch changes the effective delta, run fresh independent review against the combined commit before authorizing its push. Conflicts are repaired by pi in a fresh worktree from the current head with prior patch/source context. Retry requires fresh verify/review. Commit the integration advance only after exact remote state confirmation. Release dependents from that committed head.
7. **Publication.** After all required packages integrate, verify phase checks on the exact proposed head. Schedule inspect_target before PR publication. If it moved, stage the phase delta on the new target and reverify. Material delta changes require independent review. Conflict goes through bounded repair or parking. Then advance the integration ref by expected-head conditional update and issue the PR intent. Stage ordinary phase work from the logical initial head even before the remote integration ref exists. Its first advance expects remote absence. On a normal final check with no target drift and equal confirmed integration/head Sha, skip redundant advance. Design D1 §3 permits explicitly independent outputs. **[PROPOSED DESIGN DECISION]** Represent those as separately planned delivery groups with disjoint package sets, no cross-group dependency, and a distinct integration lane/ref, all under the same phase. If no groups are supplied, create one. A phase is delivered only when every required PR is confirmed. For non-code, acceptance of every required file and review verdict commits the handoff in PostgreSQL and enables download. There are no network actions to submit, publish, or distribute files.
8. **Cancellation and recovery.** Cancel locks the phase and stops new work. Queue stop for active attempts and cancel unclaimed work. Do not report final cancellation until live attempts are proven stopped/resolved and outstanding publication intents are reconciled. `declare_unrecoverable` accepts operator evidence of permanent loss or missing record only for an unresolved unavailable attempt. A returned observation of unknown can also park automatically. A disconnected runner does not automatically become unrecoverable. `abandon` requires the exact attempt already parked with an unknown outcome and a nonempty reason. Atomically invalidate it and release its claim. Retry with a new ID and isolated worktree/ref only where permitted. Late events cannot change workflow state or revive commands. For an ambiguous GitHub mutation, abandonment of its execution attempt does not abandon its publication intent. Reconciliation of that same intent precedes any new effect on its lane. If monitor evidence shows a success already exists, commit reconciliation without a second write.

**[CONFLICT]** GitHub ref verification and PR creation cannot be one atomic operation with a concurrent update to the target branch. Check target and exact head immediately before publication and again during result reconciliation. If target moved, record the existing PR if created, withhold delivered state and resume the same lane's target-drift verification against the observed target. Reuse the existing PR and confirm its new authorized head after any corrected integration update. Delivery attests to explicit base/head SHAs checked at handoff. Later target changes remain visible in GitHub for the operator's merge decision.

### State release invariants

| Entity | Allowed progression and release condition |
| --- | --- |
| Phase | intake → planning → execution → delivery → delivered. Waiting for an interview answer is intake or planning with an open-question set. Any nonterminal phase can park with a reason or enter canceling. Canceled requires proven resolution of claimed effects. A parked unknown remains recoverable through evidence or the precise abandonment action. |
| Package | blocked → ready → active → verification → review → integration → integrated (code), or review → accepted (files). Repair/interruption can return to ready with a fresh job, subject to budget. Unrecoverable/unknown reasons park. A held active owner is unchanged by liveness. |
| Attempt | claimed → running → terminal. Claim may become terminal without running if positively shown never started and canceled. Unknown outcome is an unresolved parked attempt with ownership. Late valid evidence can reconcile it while it remains current. Abandoned invalidates its ability to progress. |
| Intent | recorded → confirmed or unresolved. On no-effect proof the same recorded intent may be replayed. An unresolved intent holds publication authority for its lane. After confirmation no retry may create a new effect for that intent. |
| Command | pending → accepted, rejected, uncertain, target_finished or stopped. A cancel remains pending at phase level until process-stop and other effect evidence commit. Finish_debug acceptance is not successful phase completion without the exact final checkpoint result. |

### 8.4 Durable runner lifecycle

**[PROPOSED DESIGN DECISION]** Retain a runner journal with marker for permanently provisioned generation, boot ID, pending claim requests, verified grant inputs, launch intent, per-attempt process identity, immutable spool cursor, command intentions/dispositions, artifact/PR checkpoints and terminal record. Store data under a runner-owned service directory on a local filesystem. Sync records before acknowledging persistence to another process or starting consequential work. When scanning after power loss, discard only a torn unacknowledged trailing record with a valid preceding prefix. A broken prior segment makes that attempt uncertain.

1. On start read journal and obtain the machine boot identity. Keep an exclusive process lock on the state directory. Reconcile before claiming. Report only observations supported by durable records. If connectivity drops, supervised children remain under the same runner and it continues spooling. On reconnection submit recovery and replay unacknowledged events in order before claiming new work for affected slots. Re-submit Recovery after replay to finalize admission status. An active reconciled attempt can continue while another available slot claims work. Await a Directive acknowledging reconciled disposition before reissuing a pending claim or requesting a new one.
2. Before contacting `GET /jobs/next`, write the UUID and requested slot. A recovered grant uses the same request ID and attempt. Write received grant and launch intent before any process or Git operation. A local intent with no terminal record is never a permission to relaunch the same attempt. A provably never-launched grant can be run once, with the same attempt ID.
3. The runner service owns subprocesses and their descendants in its systemd control group with `KillMode=control-group`. The approved subprocess identities cannot migrate out. Record boot ID, service activation identity and PID/start identity so a recycled PID cannot prove liveness. An ordinary orchestrator restart leaves runner supervision intact. On runner restart, require evidence the old service activation ended and its execution group emptied, or a changed boot ID, before reporting stopped if a durable terminal result is absent. Ambiguous process identity remains unknown. Probe the stop semantics in M1 and acceptance, including surviving descendant checks.
4. For an ordinary production RPC job, finish on the first qualifying reported terminal turn, or classify the output as missing completion and stop that attempt. Close and verify subprocess exit before capturing final candidate. For a one-shot invocation, require successful process result and the measured terminal signature. After final assistant/check command and any artifact or ref materialization, append and sync final evidence before sending final. Mark stopped only after process exit/cleanup confirmation where applicable. Contiguous event acceptance commits a single final transition. Keep the retained journal even after acknowledgment according to §9. If uploads are pending, spool the local upload reference and defer the final event upload until the associated FileRefs are durable; maintain event sequence order.
5. Observe recovery directives. A stale attempt still live must be stopped as best effort on reconnect. Unreported stale data may be acknowledged as stale audit, without running workflow transitions. Preserve the underlying reason and disposition in control state. Never revive an abandoned ownership claim.
6. Initial registration enrolls one generation. An unrelated new generation requires operator provisioning and safe disposition of held claims. Loss of journal storage requires explicit recovery; it does not reset server ownership. Restoring a control DB with older records starts in drain, audits orphan runner claims against repo and journal, and never maps an orphan by package name to a new attempt.

**Command controls.** The Command action variants in §5.1 include `continue_debug` (checkpoint and verification feedback) and `finish_debug` (passed checkpoint). Only workflow transitions issue these. The runner records a command dispatch intent before sending it across the RPC boundary. Deduplicate by command ID. A response reports accepted or rejected for steering/continue. If a crash or EOF leaves RPC delivery uncertain, record uncertain and do not automatically inject the same message again. Stop takes precedence, is repeatable, and uses the measured abort then service-managed process stop where necessary. It resolves to stopped only after confirmed termination. A finish targets the precise checkpoint and an idle debug process. Result and final events update command and attempt states in order.

### 8.5 Runner workspace, Git and file operations

**[PROPOSED DESIGN DECISION]** Use a runner-owned Git object cache per enrolled repo and distinct worktree per attempt under its UUID. Agent-write permission applies only to the assigned production workspace and output directory. The runner owns repository administration, cache and publishing configuration. Verifiers run commands under their own identity on a disposable snapshot of the pinned input and may write only their own scratch and test output. Frontier reviewers receive read-only candidate, requirements and evidence files in a distinct snapshot. No subprocess receives runner authority to choose a push ref or interact with GitHub credentials. Allow multiple slots only with per-slot isolation. Workers never modify another slot's files or the active integration tree.

| Operation | Required mechanics |
| --- | --- |
| Snapshot and push | Runner stages allowed file changes, records full commit identity, and sends only to `refs/heads/wp/<phase-id>/<package-id>/<attempt-id>/candidate` for ordinary attempts or `refs/heads/wp/<phase-id>/<package-id>/<attempt-id>/checkpoints/<turn>` for debug. Use `refs/heads/cursus-stage/<phase-id>/<group-id>/<attempt-id>` for integration staging. Each staged or attempt ref expects absence or exact existing SHA only. Reconcile ambiguous response by remote ref read. |
| Advance integration | Use `refs/heads/cursus/<phase-id>/<group-id>`. Require intent, exact proposed SHA and old expected SHA or expected absence. Use Git ref compare-and-set semantics. An equal desired remote ref confirms replay; any unrelated ref parks. Verify publication permissions locally and the remote ref after an ambiguous write. |
| PR delivery | Use GitHub REST with runner-owned HTTPS credentials. Query all states for exact repository, head and base before creating. If matching open PR exists, validate returned head and reuse. If closed or merged unexpectedly, park with remote identity; never silently open a second one. After an ambiguous creation, reconcile by exact head/base. Retry only when remote state proves no matching PR after GitHub's completed operation can be observed. If outcome remains uncertain, retain intent and park instead of blind replay. No target update request exists. |
| Non-code handoff | Collect only validated regular files in the dedicated worker output area, reject path escapes and symlinks, and enforce type/size limits. Upload by immutable ID/digest. Provide exact downloaded bytes to verifier and review of Files. Completion only after the last required approved FileRef is confirmed downloadable. |

## 10. Observability

Use structured journald logs on both hosts. Include service, version, IDs, severity, event class and error code. Sanitize before any log or spool write. Record normalized prompts and responses in coordination when needed for the audit; redact known secret values and report redaction. Do not log auth headers, signed cookies, environment dumps or credential files. Distinguish provider failure, protocol incompatibility, command rejection, integration refusal and operator intervention.

The browser/CLI read path reports phase state, ready/claimed job counts, active slots, last runner contact, spool backlog, command disposition, retry use, parked reason and delivery references. Record observed usage only when reported by a CLI. Unknown usage is displayed as unknown, never zero by default, and does not enter workflow decisions. Report readiness separately from reachability. Routine liveness failures require no operator action. The operator runbook explains how to inspect the journal and reconcile parked work.

## 11. Error Handling

| Error | Interface and state behavior |
| --- | --- |
| Invalid input, unsupported or over-limit body | 400/422 for malformed or invalid request; 413 for size; Problem with stable code; no state change. |
| Missing/wrong principal | 401 for runner bearer; 403 for missing/mismatched operator or unauthorized action; hide foreign entity existence with 404 after authentication. |
| State, sequence or replay conflict | 409 with safe state/problem detail. Event gaps include next expected Seq. Matching replay returns committed result. No state advancement on mismatch. |
| Dependency temporarily unavailable | 503 with safe code at request time. A blocked claim returns no work. The runner keeps its journal, backs off and reconnects. |
| Execution terminal error | Classify auth, forbidden tool, protocol, failed check, timeout, canceled, interrupted, unknown, storage or Git ambiguity. Noninteractive auth or protocol configuration failures park the affected path. A proven interrupted execution may use bounded step retry. Unknown preserves ownership. |
| Publication or artifact ambiguity | Reconcile from durable intent and independent reference/digest. A mismatched result parks. An artifact file already present without metadata is reusable only on exact digest match and owned attempt; otherwise quarantine and report. |

A timeout may stop a local process under configured execution/command limits. A timeout alone never proves the stop, never releases ownership, and never authorizes a second Git mutation. The authoritative result is a committed state after validating recovery evidence. Process restart and retry have deliberately distinct effects.

## 12. Testing Strategy

**Test-construction rule.** A test may not hand-build state that the code under test is supposed to produce. Establish pre-existing Cursus state by calling the production path, never by direct fixture writes. Setup may provision accounts, an empty database, repositories and external boundary fixtures. Populate claims, accepted candidates, evidence, artifact metadata and PR intents only through their production routes and runner behavior. Capture and assert resulting persisted state through reads. Fault injection interrupts real boundaries or substitutes external transport responses, never bypasses a producer to pre-satisfy a consumer.

| Test | Production entry and expected outcome |
| --- | --- |
| Unit rules | Pure validation and deterministic transition cases. Reach nontrivial predecessor state by successive `workflows.decide` inputs or by the integration path. Reject graph cycles, counterfeit results, wrong seat, stale ownership and invalid acceptance. |
| Core pipeline | Bootstrap against empty PostgreSQL and a controlled Git remote. Start a run via CLI/HTTP, let runner claim, produce, verify, review and publish. Confirm exact push/ref and PR identity. Simulate CLI external formats with executable boundary fixtures; retain real CLI run evidence separately. |
| Crash and reconnect | Kill VPS-B after claim commit before response, after event commit before ack, and during phase sequencing. Drop the tailnet path across multiple missed heartbeats. Expect one ownership chain, no duplicate execution and replay convergence. Kill runner before launch after grant record, after launch intent, after a final spool write and after ambiguous RPC dispatch. Confirm stop evidence or parked ownership instead of inferred retry. |
| Publication and Git | Terminate runner/connection after external ref/PR write and before local record. Resume the same intent, reconcile exact effect, and demonstrate no second PR or target write. Exercise out-of-date branch head, target drift, overlapping work, repair limits, and asynchronous GitHub failure. |
| Debug loop | Supply a real failing repo condition. Start debug via intake, produce a checkpoint, verify a failed check, continue same RPC session, verify fixed checkpoint and obtain reviewed PR with no routine stop action. Exercise disconnected steer, duplicate command ID, cancel and late results. |
| Artifact and restore | Run non-code input to ready artifacts via accepted review. Interrupt upload before and after metadata commit. Reconcile to one downloadable file. Restore a matching backup bundle while runner is disconnected, then reattach and confirm held/orphaned claims are resolved safely. |
| Identity and resource isolation | Exercise both operator devices through Serve, a wrong identity, injected headers, CSRF, runner-token use on operator routes, and invalid artifact access. Prove subprocesses lack parent credentials and frontier write authority using the pinned VPS-A capabilities. Verify service remains usable with runner slots full. |
| Real qualification | Perform §14 against intended versions, hosts and trusted work. Boundary fixtures do not substitute for this evidence. |

## 13. Build/Run/Deploy

1. Initialize repository, SemVer/changelog and packaged entry points. Build a wheel with the standard Python build front end and install locked dependencies in per-service virtual environments. Proposed developer verification is `python -m unittest discover -s tests/unit` and `python -m unittest discover -s tests/integration` with empty test DB and controlled external endpoints provisioned as directed in the runbook.
2. M0 provision tailnet access, database/service users, CLI identity and credential paths, local secret files, repository enrollment and storage roots. Confirm non-interactive auth under each exact service user, including renewal. Document versions and credentials without copying secrets into the repo.
3. VPS-B bootstrap migrates with exclusive migration lock, validates schema and starts the orchestrator/HTTP loops and local socket. VPS-A bootstrap validates its profile, starts runner as a systemd service and performs reconciliation before claims. Install Serve with the configured HTTPS name and loopback backend. Verify proxy identity and access before enabling browser intake. Tagged worker node authenticates separately by bearer.
4. M1 exposes `cursus submit --input PATH`, `cursus action --input PATH` and `cursus status [--phase-id UUID | --attempt-id UUID]` on the local operator socket. `submit` reads an Input JSON document and wraps it in a submit Action. `action` reads an Action JSON document. Both use `-` for stdin and accept optional `--idempotency-key UUID`, otherwise generate a fresh key and print it with the structured response. `status` without a selector reads the operator overview. The maintenance CLI uses `cursus maintenance --input PATH` with the same input and idempotency conventions for MaintenanceRequest. `--help` does not connect to services. Successful requests print JSON and exit 0; invalid or rejected requests print structured Problem and exit nonzero. Payloads match §§5–6 and 15.3. Browser delivery in M3 exposes the same actions without requiring installation on operator devices. Use an SSH/admin shell on VPS-B for M1 command-line access.
5. Release from the same git revision for code, migrations, role/prompts and docs. M1 one-package path first, M2 multi-package/debate/debug and recovery, M3 browser surface, M4 non-code workflows. Tag each milestone only after its test evidence. On upgrade drain new claims, preserve journals and immutable references, apply forward migrations and reconcile before reopening. Take and test a restorable backup before an incompatible migration. Never reset state or replay a remote mutation to downgrade.

## 15. Seam Register & Call Traces

### 15.1 Composition root and trace conventions

The single composition module is `src/cursus/bootstrap.py`. It constructs control-side, runner-side and local CLI infrastructure in the corresponding process mode as specified in §8.1. The runner never constructs a Store or a database client. The control plane never constructs a CLI subprocess, repository workspace, or GitHub publisher.

In the traces, **B/DB** means committed PostgreSQL state on VPS-B, **B/files** means immutable bytes on VPS-B, **A/journal** means synced state and ordered spool on VPS-A, **A/workspace** means runner-owned local Git/files plus isolated process workspace, and **GH** means GitHub reference or PR state. Each arrow crosses the named module seam or invokes the indicated external boundary. In-process transitions are called inside the designated transaction. The normal state changes described here occur only on commit.

### 15.2 Primary runtime call traces

**T01 — Start and intake.** On VPS-B systemd calls bootstrap control mode → `config.load` reads local settings/role release → bootstrap constructs services → `store.migrate` applies migrations under lock and `http.serve` exposes the loopback and socket ingress → bootstrap calls `control.maintain` for boot scan. A browser sends Action to `http.serve`, or local CLI bootstrap calls `http.request_local` to the same operator route on the socket → HTTP authorizes and invokes `contracts.validate` → `control.action` → `store.transact` loads current Snapshot and calls `workflows.decide` with Action; Store applies Decision and commits phase, spec and first Job plus events/request key [B/DB]. HTTP returns Reply. For an enrolled repo source or coding base resolution, T02 delivers resolve_input to the runner → `repository.perform` reads pinned blob/ref [GH → A/workspace] → runner returns Final containing exact UTF-8/SHAs through T03 → committed spec and next interview/plan Job [B/DB]. Failed source resolution cannot create an accepted spec.

**T02 — Assign and start.** VPS-A systemd calls bootstrap runner mode → `config.load` and bootstrap constructor wiring → `runner.serve` performs T08 if required. For each eligible slot, `runner.record` persists request UUID [A/journal] → `runner.exchange` requests claim → `http.serve` validates bearer/generation and claim parameters → `control.runner_request` → `store.transact` records attempt and ownership/claim for the exact request UUID [B/DB], returns Poll. With no ready job, HTTP calls `control.wait` → `store.wait` outside a transaction and rechecks until deadline. On grant, runner validates the Job and `runner.record` persists Claim and launch intent [A/journal] → `repository.perform` sets up any pinned workspace/files [GH, B/files → A/workspace] → `execution.run` invokes direct CLI or enrolled verifier under its authorized identity, or runner calls `repository.perform` for a runner-owned step. Runner records start and ordered outputs before transmission [A/journal]. A committed grant with a lost response starts no local process before T08.

**T03 — Report and advance.** Runner captures execution event → `contracts.validate` normalizes into a legal Event → `runner.record` appends and syncs it [A/journal] → `runner.exchange` POSTs ordered Event batch → `http.serve` authenticates and validates → `control.runner_request` → `store.transact` compares Seq and digest; for Final, checkpoint or confirmed observation, invokes `workflows.decide` with committed Snapshot → store commits Ack, state, evidence reference and resulting Job/Command [B/DB] → runner records acknowledged Seq [A/journal]. A status/log/usage event updates its projection without fabricating a workflow result. If an artifact is required, T07 completes before the associated Final becomes eligible to send. Unknown or stale events follow T08 guards. This path drives every named step below unless an exception is explicit.

**T04 — Guided intake, planning and debate.** T01 enqueues interview or plan. T02 invokes the configured frontier binary; T03 accepts questions or typed result. For a required answer, HTTP invokes `control.action` → Store and Workflow commit answer and next interview Job [B/DB]. A finished spec revision advances through optional spec debate and then plan. A bounded scout request schedules `scout` via T02, T03 commits evidence and requeues the original planner with that evidence. For debate, each typed Final triggers the next fresh frontier seat by the same path. A judge's unresolved question pauses in guided intake; answered revision feeds the next round. A validated plan/accepted debate triggers production jobs [B/DB]. Exhaustion commits parked state. No CLI sends jobs to another CLI.

**T05 — Coding, review, integration and PR.** T02 executes produce via `repository.perform` to pin worktree → `execution.run` pi → runner validates completion report and calls `repository.perform` to capture commit and push an attempt ref [A/workspace → GH] → T03 records Candidate [B/DB] and queues verify. T02 materializes that candidate, executes verifier and returns Evidence via T03. T02 next supplies immutable candidate/evidence to the independent reviewer and T03 commits verdict. On repair, a new package job repeats from pinned conditions, within budget. On accept, stage_integration materializes commit/effective delta [A/workspace → GH staging ref]; Final leads to verify and, on changed delta, review. Successful evidence causes Store to commit a publication intent and advance_integration Job [B/DB]. T02 runner calls `repository.perform` to inspect current GH head, conditionally update ref and read it back [GH]; T03 commits integrated head and releases dependents [B/DB]. When lane finishes, the same path verifies final head and calls inspect_target to handle target drift before committing publish_pr intent. `repository.perform` finds or creates exact PR and confirms its identity [GH]. T03 commits handoff. No runner stop or missing acknowledgment resolves a publication intent by itself. T08 reconciles ambiguous actions against remote effects before any repeat.

**T06 — Iterative debugging and steering.** T02 launches pi RPC under a debug claim. `execution.run` returns a turn result without terminating the session → runner calls `repository.perform` to save/push the immutable checkpoint → T03 accepts checkpoint and queues independent verifier. Verification Final → `workflows.decide` commits `continue_debug` or `finish_debug` [B/DB]; active runner heartbeat exchanges Directive → `runner.record` persists command intent → `execution.run`'s command stream calls pinned RPC or closes finished process → T03 records actual command/final disposition. On failed evidence the same pi process gets feedback; on successful evidence, the finalized exact passing checkpoint enters review and T05 integration/delivery. For operator steer/cancel, `control.action` commits Command/phase status under Store, Directive transports to existing attempt, then local intent, measured RPC and terminal confirmation follow the same path. No command can be consumed by a replacement attempt.

**T07 — Non-code artifacts and delivery.** T02 starts pi production against workflow requirements and predecessor FileRefs. Runner calls `repository.perform` to collect allowable files [A/workspace], records digest and pending receipt [A/journal], and `runner.exchange` uploads each file → HTTP validates metadata and bearer → `control.runner_request` authorizes claim → `artifacts.stage` streams, hashes and atomically stores bytes [B/files] → `store.transact` records exact metadata [B/DB]. Runner records receipt and sends Final via T03. Verification and independent review fetch only declared ready inputs through `runner.exchange` → HTTP/Control/Store entitlement read → `artifacts.open` [B/files → A/workspace]. T03 commits accepted FileRefs and phase delivery [B/DB]. Operator authorized download uses T09. No external distribution step exists.

**T08 — Disconnect, crash, and unknown.** Runner restart or link recovery → `runner.serve` scans journal and known service activation according to §8.4 → `runner.exchange` sends Recovery → HTTP validates → `control.runner_request` → `store.transact`, invokes `workflows.decide` on confirmed observations [B/DB] → Directive. Runner replays eligible local records through T03, reuses existing unlaunched Claim via T02, and stops a live stale process. Server restart boot scan and missed heartbeat updates never mutate ownership by timeout. A confirmed stop releases eligible ownership and enqueues a new attempt only within budget. If unknown is reported or explicitly declared, Workflow parks with owner held. Operator abandon through T01's Action seam commits invalidation, reason and new eligibility [B/DB]. For uncertain GitHub mutation, the next allowed work item before a new effect on the lane is a reconcile_publication job for the previous intent using `repository.perform` to inspect GH; T03 commits confirmed result or leaves intent parked. Restore drain blocks ordinary claims. Once runner observations have been reconciled, the persisted restore recovery list can issue only read-only reconcile_publication jobs through the ordinary repository slot and claim/event contracts. This permits recovery without authorizing new remote effects.

**T09 — Browser observation and downloads.** Browser GET → `http.serve` verifies identity and route → `control.query` → `store.read` returns authorized View/EventPage/FileRef from B/DB. SSE sends committed cursor, delegates waiting to `control.wait` → `store.wait`, and rereads after wakeup. Browser reconnect replays by cursor or resets to authorized snapshot. For a download, HTTP opens the returned FileRef via `artifacts.open` [B/files] and streams validated bytes. Operator commands use T01, T04, T06, T08.

**T10 — Maintenance, backup and restore.** Bootstrap runs periodic trigger → `control.maintain` → `store.transact` commits reachability/admission and retention decisions. For eligible orphaned/expired files, maintenance calls `artifacts.remove` after making them unavailable [B/DB → B/files]; runner prunes only acknowledged eligible local spool entries via `runner.record` [A/journal]. Hermes calls the runbook backup CLI under the authorized local identity → `http.request_local` sends maintenance request → `control.maintain` takes cleanup hold [B/DB] → operator-admin procedure runs `pg_dump`, copies files and records manifest [B/DB and B/files → backup]. After completion the CLI records disposition and releases the hold via the same path. Restore is offline via runbook PostgreSQL and filesystem commands, then bootstrap starts under configured drain; T08 resolves ownership and publications before the local CLI reopens intake.

**Additional seam contracts.** `control.wait(deadline: Time, cursor: optional Seq) → wake/timeout` delegates to Store. `artifacts.remove(FileRef) → removed/already_absent/failed` is only for metadata already unavailable and not referenced by active or retained state; on failure maintain a retryable cleanup marker. `MaintenanceRequest` is operator-local only and is one of backup_begin, backup_end(outcome, recovery-point Time, optional manifest Digest), clear_abandoned_backup_hold(reason), and reopen_after_restore(reason). `MaintenanceDisposition` is accepted/rejected plus current drain/hold state and optional Problem. `POST /operator/maintenance` on the Unix socket takes MaintenanceRequest and request UUID and returns MaintenanceDisposition through `control.maintain` and Store. The backup caller uses `cursus maintenance`; reopen is rejected while a held claim or unresolved mutation can still advance without reconciliation or explicit isolation of the affected lane; no browser endpoint exposes it. A stale backup hold requires explicit local admin recovery after confirming no backup is running.

**Seam closure check.** T01–T10 name a route or service caller for each component in §8.1, identify where the result becomes durable, and give every §8.2 step a runtime invoker. The system can leave an outcome parked where the platform offers no reliable proof. This is a specified terminal or recovery branch rather than an assumption that worker or GitHub state can be recovered unconditionally.
